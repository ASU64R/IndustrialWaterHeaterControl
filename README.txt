WaterHeaterControlsd
   Суть проекта
Модель электрического водонагревателя. Полный цикл: нагреть воду → удержать температуру гистерезисом → при Stop/E-Stop/аварии остановить нагрев, при необходимости сбросить давление. Третий проект серии; цель — собрать смешанное управление: аналоговый тракт, машина состояний, защёлки, ручной арбитраж с force по белому списку, журнал событий, статистика. ST — средство, не цель.
   Архитектура
PLC_PRG — диспетчер: входы, HMI watchdog, порядок вызова FB, отдача журнала напрямую в GVL (aHistory => GVL_HMI_Status, без локального массива-копии).
FB_SignalConditioning — аналог: raw → EngValue → FilteredValue, Valid, обрыв/КЗ.
FB_Debounce — защита от одиночных помех дискретных сигналов и фронтов.
FB_Alarms — диагностика: SR-защёлки, aActiveAlarms[], aActiveWarnings[], eErrorCode/eWarningCode, GlobalFault, BreakSensor. Единственный автор текущего статуса аварий.
FB_WaterHeaterController — машина состояний, гистерезис, намерение нагрева, ManualAllowed.
FB_CommandArbiter — арбитраж AUTO/MANUAL/force/пермиссивы/рубильник; каскад: источник → пермиссив → рубильник safety → force (белый список).
FB_AlarmLogger — журнал: приватное кольцо aRing + публичная витрина aHistory, ленивая перестройка по Dirty, eClass, раздельные id-map.
FB_Statistics — учёт: наработка ТЭНа по final-команде, циклы нагрева, макс температура, среднее, счётчики аварий по фронтам, сброс смены пакетом.
   Режимы
AUTO — штатный нагрев/удержание по рецепту.
MANUAL — ручное управление механизмами; разрешён в рабочих фазах, не в любой момент.
Stop — мягкая остановка, возврат в Idle.
E-Stop — аварийный останов: нагрев OFF; сброс давления разрешён через force (опаснее запертый клапан, чем открытый).
   Приоритеты защит
E-Stop
Range Check / повреждение состояния машины
Перегрев (OverHeating, latch)
Обрыв/невалидность датчика (BreakSensor*, latch)
Нет нагрева (NoHeatingUP/NoHeatingHolding)
Сухой ход / низкий уровень (DryRun, LowLevelWater)
Потеря связи HMI (watchdog в PLC_PRG)
   Аналоговая часть
RawValue — сырой АЦП.
EngValue — масштабированное инженерное значение.
FilteredValue — значение для гистерезисов и управления (скользящее среднее).
Valid — валидность; обрыв/КЗ → авария датчика, безопасный режим, не слепой стоп.
Debounce — на дискретных фронтах, чтобы помеха не рождала ложное событие.
   Машина состояний
Initial → Idle → Heating_UP → Holding → Stop → Initial.
Idle ждёт Start.
Heating_UP греет до порога конвейера/удержания.
Holding держит температуру гистерезисом по FilteredValue.
Неизвестное/повреждённое состояние → безопасный переход, не работа «как попало».
Гистерезис синхронизирован с состоянием машины (не независимый таймер).
   Defense in Depth
Барьеры после CASE ограничивают выходы независимо от ветки.
Ручной режим не пересчитывает диагностику, а получает готовые флаги из FB_Alarms.
Force проходит после рубильника safety, но только по белому списку выходов (сброс давления), и логируется как событие.
Статистика считает final-команды, поэтому наработка верна и в AUTO, и в MANUAL.
Пермиссив (можно ли в условиях) ≠ рубильник (немедленно стой) ≠ force (люк оператора) — три разных слоя, не путать.
   Диагностика и журнал
eErrorCode / eWarningCode — текущая авария/предупреждение (ось статуса, автор FB_Alarms).
aHistory — витрина последних 21 событий (кольцо 0..20), автор FB_AlarmLogger; [0] = самое свежее.
Журнал пишет по фронту появления/исчезновения (SET/RESET), не по уровню; дубликатов подряд нет.
Один поток для Error и Warning через eClass; словари индекс→имя раздельные (aErrorIdMap / aWarningIdMap).
Пустая запись определяется по eAlarmId = No_Error (ось имени), не по eClass; FirstCycle инициализирует и кольцо, и витрину.
Хронология ≠ приоритет: свежая мелочь может лежать выше старой аварии; приоритет живёт в eErrorCode/GlobalFault.
При одновременных событиях одного скана политика эскалации: warning пишется в кольцо первым, error вторым → error сверху.
Кольцо затирает древнее автоматически; отдельной кнопки очистки архива нет (в отличие от сброса статистики).
   Статистика
Время работы ТЭНа (наработка по финальному выходу, интеграл под условием, не фронт).
Циклы нагрева — по фронту входа в Heating_UP (R_TRIG, одиночный сигнал).
Максимальная температура — накопитель-максимум по FilteredValue при Valid.
Среднее время цикла = наработка ТЭНа / число циклов (приближение: ТЭН может отдыхать в Holding).
Счётчики аварий по каждой защите — по переходу FALSE → TRUE (prev-массив в цикле, группа сигналов).
Сброс смены пакетом связанных величин (наработка + циклы + макс + счётчики) в источник, не в проекцию; служебное SystemRunTimeMs не сбрасывать.
Ловушка «за смену»: граница смены — внешний триггер (кнопка/RTC/SCADA), ПЛК сам её не знает.
   Ключевые принципы
Один владелец на структуру: stStatus у FB_Alarms, aHistory у FB_AlarmLogger, stStatistics у FB_Statistics.
Контроллер/alarms создают статус и события; logger их пишет; statistics их считает — потребители читают контракты, не лезут в чужие буферы.
Logger и Statistics считают свои фронты от публичного stStatus независимо; дублирование вычислений допустимо, дублирование данных — нет.
Порядок в PLC_PRG: кондиционирование → диагностика/контроллер → арбитр → статистика (после final-команд) → журнал (после статуса).
PLC_PRG не содержит бизнес-логики, только связывает блоки и публикует выходы в GVL.
VAR — состояние между сканами (Head, Dirty, prev, счётчики); VAR_TEMP — расчёт одного скана.
RETAIN — для накоплений (счётчики, наработка, циклы, макс); R_TRIG, prev, Head, Dirty — нет.
   Особенности
MANUAL/force разрешены в рабочих фазах, а не в любом состоянии.
E-Stop со сбросом давления: force после рубильника по белому списку — запертый сброс опаснее открытого.
Нет Complete: цикл завершается Stop или уходом в аварию; материальный трекинг не реализован (вода, не деталь).
Учебный период задачи — константа; на заводе брать фактический elapsed цикла.
Статистика отделена от управления; журнал отделён от текущего статуса; аналоговый тракт отделён от диагностики.
